# Yokoi - Switch port (work in progress)

This folder plays the same role for the Nintendo Switch that [`android/`](../android) plays for Android and the root [`Makefile`](../Makefile)/[`source/virtual_i_o`](../source/virtual_i_o) play for 3DS: it holds everything specific to this platform, while the emulator core stays in [`../source/SM5XX`](../source/SM5XX) (CPU emulation) and [`../source/std`](../source/std) (settings, savestate, pack loading) and is shared, unmodified, across all three.

## Status: playable, with a game/manufacturer select menu

**Confirmed working on real hardware**: pack loading, CPU emulation, rendering (background/segments/console), audio, and input all verified end-to-end (see git history / session log for the debugging trail - the first render attempt was a black screen caused by `eglQuerySurface` returning 0x0 on Switch's Mesa/nouveau backend; fixed by using `nwindowSetDimensions()` instead, which is what devkitPro's own examples do).

`switch/source/main.cpp` runs a single-threaded loop (poll input → step the CPU → render → play audio → swap), modeled on `source/main.cpp`'s single-loop design (3DS) rather than Android's separate-thread architecture (there's no touch UI / Activity lifecycle to juggle here, so the extra thread isn't needed). It starts in `switch_menu.cpp`'s select menu rather than booting straight into a game.

What exists:
- `source/core/` — game loading + layout + segment-state bookkeeping, ported from Android's `yokoi_game_loader.cpp` / `yokoi_layout.cpp` / `yokoi_segments_state.cpp`, trimmed to single-threaded (no mutex/snapshot double-buffering - nothing else touches this state concurrently); plus `switch_menu.cpp`, the game/manufacturer select menu (see below)
- `source/render/` — `switch_gl.cpp` (shader/VAO/VBO setup, ported from `yokoi_gl.cpp`) and `switch_screen.cpp` (the actual in-game draw: background, segments with mask/colored/marking passes, console overlay - ported from the `render_frame()` function in `yokoi_jni.cpp`, always in Android's "combined" panel mode since Switch only has one screen to draw into); plus `switch_ui.cpp`, a small immediate-mode 2D helper (rects/textures/text in absolute pixel space) the menu draws through - deliberately owns its own GL program/VAO separate from `switch_screen.cpp`'s, so the menu can't disturb the in-game renderer's already-verified state
- `source/input/` — `yokoi_controller_state.{h,cpp}` and `yokoi_input_mapping.{h,cpp}` copied **unmodified** from Android (they're already platform-neutral - just atomics and the `Virtual_Input` interface, no Android API calls), plus `switch_input.cpp` translating `padGetButtons()` into the same `CTL_*` mask Android's touch/controller bridge produces
- `source/audio/` — `switch_sound.cpp`, an `audrv`/`audren` backend with the same public interface as `3ds_sound.h`'s `Virtual_Sound` (push-model wavebufs, closer to `ndsp` than to Android's pull-model AAudio backend)
- `source/third_party/stb_image.{h,cpp}` — PNG decode, used for segment/background/console art *and* menu thumbnails. Android offloads this to Java's `BitmapFactory` and has no C++ PNG decoder to reuse; Switch has no such shortcut.

### Manufacturer support: Tiger + "David and John"

Merged in from a `betabranch` snapshot that was ahead of this repo's `source/` tree (SM5XX core, `GW_ROM.h`, `virtual_input.h`, `load_file.cpp`, plus the new `source/David_and_John/` tree and `source/std/David_And_John_ROM_rgds/`) - see that merge's commit for the file-by-file breakdown. Two new manufacturer categories:

- **Tiger** (`MANUFACTURER_TIGER`) - 17 licensed titles (Sonic 1/2, Street Fighter II, the Double Dragon trilogy + Super, Castlevania II, Mega Man 3, Ninja Gaiden + III, Strider, Golden Axe, Altered Beast, Gauntlet, Space Harrier II, MC Hammer). These run on the same SM510/SM511 CPU emulation as everything else - no new chip support needed, just data. **Requires the user's own Tiger MAME ROMs** run through `CONVERT_ROM` (same restriction as every other manufacturer here - no ROMs are bundled) before they'll show up in a generated pack.
- **David and John** (`MANUFACTURER_DAVID_AND_JOHN`) - 5 original, non-emulated games (Avignon, Climber, Esquive, Fabric, Rythme) built on a `David_And_John_fake_cpu` class that subclasses `SM5XX` and overrides its virtual hooks with a scripted game engine instead of real Sharp opcode interpretation - so it rides the exact same render/audio/input/savestate pipeline as a real CPU. Detected via a synthetic 4-byte ROM sentinel (`0xFF 0xFF 0xFF`) in `yokoi_cpu_utils.cpp`, and **always present** in the game list regardless of what pack is loaded (see `load_file.cpp`) - their game data is compiled in directly, no pack entry needed for that part.

**Confirmed working on hardware** (Tiger): once a pack is regenerated with the user's own Tiger MAME ROMs, Tiger games load, render (segments/background/console), and play correctly - verified against Double Dragon, Gauntlet, and Sonic the Hedgehog.

David and John's artwork wasn't wired into `CONVERT_ROM/convert_3ds.py`'s pack writer initially - nothing in that pipeline referenced `gfx2x_open_source/` at all, on either branch, so those 5 games loaded and ran but rendered as solid blocks (the renderer falls back to a plain white texture for any segment whose atlas failed to load - same fallback that caused the "tofu box" look during the font bug earlier). **Fixed**: `write_rom_pack_v1()` in `convert_3ds.py` now also bundles every `gfx2x_open_source/*.png` by filename for non-3DS (`.png`-texture) targets, the same way it already bundles the UI textures (`texte_3ds.png`, `logo_pioupiou.png`). Regenerating the pack after this fix should give David and John full art, no MAME ROMs required since their content is original.

**To pick up either of these**: regenerate `yokoi_pack_rgds.ykp` via `CONVERT_ROM` and redeploy per "Testing on hardware" below - a pack built before this merge won't have any of the new data (Tiger also still needs the user's own Tiger ROMs added as `CONVERT_ROM` input first).

### The menu (`switch_menu.cpp`)

Styled after [Hekate-Toolbox](https://github.com/CTCaer/hekate)'s dark theme (`source/gui/theme.c`'s `ColorSetId_Dark` palette: `#313131` background, `#59EDC0` accent, `#0ABFFF` highlight text) and bar layout, but with **this project's own navigation semantics** rather than Hekate's icon grid, ported from the menu-navigation half of Android's `render_frame()`:

- **D-pad Left/Right** — next/prev game within the current manufacturer
- **D-pad Up/Down** — next/prev manufacturer (restores its last-played game, if any, this session)
- **A** — start the selected game
- **Minus** — cycles the game list's sort mode (Manufacturer / Alphabetical / Date); Up/Down then jumps by whatever the current mode groups by instead of always by manufacturer.
- **Plus** — opens the settings screen (rotation, background color, segments, console art, load state behavior, log file) from the game list. Free to use here because during gameplay Plus is mapped to the G&W "A" button instead, and gameplay never routes input through this menu's update function at all.
- **L+R+Plus** — quits to hbmenu, game-list only.
- **ZL+ZR** — gameplay only: pauses and opens the in-game settings screen (see below). Chosen over reusing L+R+Plus there because ZL/ZR do nothing else during gameplay at all (L=Time, +=Game A, −=Game B all already mean something), so - unlike L+R+Plus - there's no risk of an accidental trigger and no third button is needed to guard against one; just holding both is enough. This is the *only* way to pause/menu out from gameplay - B is deliberately not used, since several G&W games use it as a real gameplay input.

### Settings (`switch_menu.cpp`'s settings sub-screen, `switch_settings.h`/`.cpp`)

Opened with **Plus** from the game list, or with **ZL+ZR** during gameplay (see "In-game settings" below for how that entry point differs). Up/Down selects a row, Left/Right changes its value, B or Plus closes it. Every change applies live (the same `g_settings`/`g_screen_rotation` globals the renderers read every frame) and is written to disk immediately, so there's no separate save/cancel step.

- **Rotation** — 0° / 90° / 270° (180 deliberately skipped). Rotates *both* gameplay and the menu itself: the vertex shader's `uRotCosSin` uniform (already present from an earlier, paused rotation experiment) rotates the final NDC output, while all layout code upstream of it (the game canvas fit in `switch_screen.cpp`, and every pixel-space coordinate in the menu) is computed against width/height-swapped "logical" dimensions at 90/270. Because NDC is a symmetric [-1,1] square regardless of aspect ratio, fitting against the swapped aspect and then rotating the result is exactly equivalent to fitting a genuinely rotated viewport, with no distortion - this is why no other layout math needed to change. (The sign of `uRotCosSin`'s sin component needed flipping from the naive rotation-matrix math to match what actually came out right on hardware - see the comment at both call sites if this ever needs revisiting again.)
- **Background Color** — the same 6 presets `AppSettings`/`BACKGROUND_PRESETS` already define (`../source/std/settings.h`), cycled like Android's spinner, plus a 7th **Custom** slot past Cream.
- **Segments** — a 3-preset None/Light/Dark cycle over `AppSettings::segment_marking_alpha`, matching Android's `SettingsMenu.java` spinner rather than 3DS's raw 0-255 stepper (both platforms edit the exact same underlying field - Android just presents it as friendlier presets), plus a 4th **Custom** slot past Dark.

**Custom Background Color / Segments**: selecting either row's Custom slot reveals a second, indented row right below it - **Enter Custom Color** / **Enter Custom Value** - which **A** opens as a text entry via libnx's `swkbd` applet (a single blocking `swkbdShow()` call; the frame loop is already paused on this modal screen anyway, so no async handling is needed). Background uses a full keyboard capped at 6 characters (hex digits only, validated after the fact - there's no dedicated hex-only keyboard type); Segments uses `SwkbdType_NumPad` capped at 3 digits, matching 3DS's own 0-255 range. An invalid result (wrong length, non-hex/non-numeric, or out of range) is silently discarded and the field resets to blank - which is also what happens if Custom is left selected with nothing ever typed - and the *applied* color/value falls back to Light Yellow / Light respectively, per explicit request; a valid entry applies immediately and persists exactly like any preset (`g_settings.background_color`/`segment_marking_alpha` don't care how they got their value). Cancelling the keyboard leaves everything as it was. Neither "Custom is selected" nor the raw typed text is itself persisted - `bg_color_display()`/`seg_display()` already fall back to showing a raw non-preset value on their own, so a genuinely custom stored value still displays correctly after a restart without needing that; `switch_menu_init()` re-derives whether to start on the Custom slot (and pre-fills the entry text) by checking whether the loaded value matches any preset at all. Like every other row here, Custom entry is locked out entirely under the hidden `debug` flag (see below) - in practice this falls out for free, since Background/Segments themselves are already locked then, so Left/Right can never reach the Custom slot that would reveal these rows in the first place.
- **Single Screen Game Console Art** — Hidden (default) / Shown. Hides the decorative "console art" strip (`GW_rom::console_info`, the handheld's plastic-case artwork drawn below the real screen - `kRenderConsoleOverlay` in `switch_screen.cpp`) so the actual game screen can use that space instead. This is a different concept from Android's "top screen only" (see below): it only ever affects games that have a console-art strip in the first place, which is exactly the games going through `switch_layout.cpp`'s `!g_split_two_screens_to_panels` branch - single-screen games, and "double_in_one_screen" games (two real screens shown side by side, still with a console strip below them both). True dual-screen "clamshell" games (`g_split_two_screens_to_panels`) have no console strip at all - their "bottom" is a second real screen, not artwork - so this setting can't touch them and needed no special-casing to exclude them. David & John games never populate `console_info` either, so they're naturally unaffected too - none of this required a manual per-game list, the existing layout flags already carried the distinction. `switch_layout.cpp`'s `rebuild_layout_from_game()` skips reserving canvas space for the strip when hidden (recomputed on every game (re)load, including resuming the same game from the menu, so a mid-session toggle takes effect the next time A is pressed) and `switch_screen_render()` skips drawing it.
- **Load State Behavior** — Ask (default) / Auto-Load / Never Load. Governs what happens when A is pressed on a game with an existing save file: Ask shows the load prompt (see "Save states" below), Auto-Load skips the prompt and restores it immediately, Never Load always starts fresh without ever touching the save file (which still isn't deleted - it just sits there, as always, until the next real exit silently overwrites it).
- **Log File** — Off (default) / On. Runtime hook into `../source/std/debug_log.h`'s new `debug_log::set_enabled()` (see below) - toggling this immediately opens or closes `yokoi_log.txt`.
- **Beta Games (Tiger, David and John)** — Off (default) / On. Shows or hides every Tiger and David & John game from the game list *and* the visible game count - `rebuild_sorted_order()` in `switch_menu.cpp` filters them out of `g_sorted_order` (the one list every bit of navigation, the bottom counter, and Up/Down group-jumping all walk) whenever this is off, so hiding them is a single filtering point rather than something every call site has to know about. Turning it **on** requires confirming a beta-support warning screen first (**A** enables, **B** cancels) - a separate modal layered on top of the settings screen (`g_betagames_confirm_active`), not an instant toggle. Turning it **off** is instant, no confirmation. Save files for beta games are never touched either way - purely a visibility switch. If the game list's current selection or `lastgameplayed` (see "Save states" below) is a beta game at the moment this gets turned off, both get moved off it automatically: the selection lands on whatever's now first in sort order (the same fixup `rebuild_sorted_order()` already does for any other case of the selection going stale), and `lastgameplayed` resets specifically to `AC_01` so it's never left pointing at something now invisible.

Console Art, Load State Behavior, Log File, and Beta Games are only shown from the game-list entry point - see "In-game settings" below for why the in-game one only has three rows.

**Persistence is Switch-only and intentionally not shared with 3DS/Android**: `switch_settings_load()`/`switch_settings_save()` (`switch_settings.cpp`) read/write a plain-text `sdmc:/switch/yokoi/yokoi_settings.txt` (`key=value` lines: `background_color`, `segment_marking_alpha`, `rotation`, `hide_console_art`, `loadstate`, `enable_log`, `lastgameplayed`, `betagames`) instead of the binary `yokoi_gw_settings.dat` that `../source/std/settings.cpp`'s `load_settings()`/`save_settings()` write for 3DS/Android - requested explicitly so the file can be opened and edited by hand. Those shared functions are untouched; `main.cpp` just calls `switch_settings_load()` instead of `load_settings()` at startup. Screen rotation and everything below Background Color/Segments have no shared-core equivalent, so they all live in `switch_settings.h`, not in `AppSettings`.

**Hidden `debug` flag**: not a settings-menu row at all - the only way to set it is hand-editing `yokoi_settings.txt` to add `debug=1`, and it's never written back once read (`switch_settings_save()` no-ops entirely while it's set, for the rest of that run). Meant for inspecting a specific on-disk configuration without the app being able to alter or "fix" it out from under you. With `debug=1`:
- Every settings *value* row except Rotation is locked read-only (dimmed, Left/Right do nothing) and displays whatever raw value the file actually held - including a value outside the normal presets, since loading never snapped values to the nearest preset to begin with (only the cycling logic does, to have a starting point). The settings screen's title also gets a `(DEBUG)` tag as the only in-app indication this is happening. The in-game screen's "Return to Main Menu" row is exempt from this dimming - it's a navigation action, not a setting, and always stayed fully functional under debug mode; it just used to *look* locked too, which was a rendering-only bug (`action_row` wasn't excluded from the dim check) fixed once reported.
- Rotation still changes freely, but only in memory - `switch_settings_save()` being a full no-op covers that case too, nothing special needed for it specifically.
- Save states are bypassed completely: `switch_unload_current_game()` skips the save (so `lastgameplayed` - see below - never updates either), and the game-list A-press always takes the fresh-load path, ignoring `save_state_exists()` and Load State Behavior entirely.
- Logging is force-enabled (`debug_log::set_enabled(g_log_file_enabled || g_debug_mode)`) regardless of the `Log File` setting's actual stored value - lets a run be inspected without also having to edit `enable_log` (which would itself be locked from saving anyway once `debug=1` takes effect).
- Beta games are force-visible the same way (`betagames_visible()` in `switch_menu.cpp` ORs `g_debug_mode` in alongside `g_betagames_enabled`), without ever flipping or saving the stored `betagames` value either.

**In-game settings** (`switch_menu_open_ingame_settings()`, reached via ZL+ZR during gameplay instead of the old direct-to-menu behavior): the same screen and same three adjustable rows (Rotation/Background Color/Segments - all still apply live to the running game), but with two differences, tracked by a single `g_settings_from_gameplay` flag:
- The Console Art row is replaced with a **Return to Main Menu** action row (confirmed with **A**) - Console Art only takes effect on a game's next (re)load (see above), so it would silently do nothing if changed here, and got left out rather than ship a dead control.
- **B** (or Plus) resumes the paused game in place instead of returning to the game list - no reload, `g_cpu`/`g_game` are untouched throughout, it's a true pause/resume. Opening the screen doesn't need any separate "pause" step either: it works by calling the same `switch_menu_return_to_menu()` the game list's return path already used, which flips the `g_menu_active` flag `main.cpp`'s loop already checks before stepping the CPU or rendering gameplay - so "pause while this menu is open" was already a side effect of the existing control flow, not new state to track. The top-left title also swaps from "YOKOI" to "PAUSED" as a visual cue that a game is suspended underneath.

**Deliberately not included yet**: Android's own "top screen only" toggle (`SettingsMenu.java`'s `topOnlyBtn` / `MainActivity`'s `singleScreenTopOnly`) - switches *true* dual-panel "clamshell" games between rendering both real G&W panels stacked vs. just the top one filling the screen. Not the same problem Console Art above solves (that one only ever touches decorative artwork, never a real second screen) - this would need an actual panel-filter parameter threaded through `switch_screen_render()`, which still doesn't exist.

### Save states (`switch_unload_current_game()` in `switch_game_loader.cpp`, the load prompt in `switch_menu.cpp`)

`../source/std/savestate.h`/`.cpp` is fully shared and needed no porting - one `.sav` file per game at `yokoi_gw_saves/<game->ref>.sav` under the same `sdmc:/switch/yokoi` root everything else uses, keyed by the game's stable `ref` (survives pack reordering), holding a small header plus whatever `cpu->save_state()`/`load_state()` write (every CPU type implements it, David & John's fake CPU included). The behavior wrapped around it follows **3DS's model**, not Android's - 3DS keeps its `SM5XX*` instance alive across a return-to-menu (save is a parallel backup, not the only way to keep progress) where Android fully tears its CPU instance down on every return; Switch's existing pause/resume design (instant resume via the in-game settings screen's B) already matches 3DS's, so this reuses that instead of introducing Android's unload-and-reload-every-time model.

- **Prerequisite that had to be fixed first**: `switch_menu_open_ingame_settings()`'s "Return to Main Menu" row used to leave `g_cpu` fully loaded in the background once back on the game list (matching the old pre-settings-menu L+R+Plus behavior, which only ever paused, never unloaded) - so it was possible to be looking at the game list with an in-progress game silently sitting behind it with no save file backing it up. Fixed by adding `switch_unload_current_game()` (`switch_game_loader.cpp`): saves the current game's state (no-op if nothing's loaded) then resets `g_cpu`/`g_input` and clears `g_game`/`g_segments`. The "Return to Main Menu" row calls it directly - it's now the one place that actually commits to leaving a game, as opposed to just pausing to show that screen (which still keeps the session alive for B-to-resume, unchanged). It's also called as a defensive no-op-when-safe backstop in two more places: right before quitting to hbmenu from the game list (L+R+Plus there), and unconditionally right before `main()` returns - covering exits `appletMainLoop()` itself ends, e.g. a forwarder's process being force-closed from the HOME menu mid-game, which goes through neither of the other two paths. With this fix, the game list can never be reached with something still loaded - there's nothing left to lose no matter how the app closes from there.
- **Load prompt**: pressing A on a game that has a save file (`save_state_exists()`) shows a "Load Save State? [A] Load Save / [B] Start Fresh" screen instead of loading immediately - skipped entirely for a game with no save, which just loads fresh exactly as before (3DS's behavior; Android always shows an equivalent prompt even with nothing to load, forcing the choice to "fresh"). Confirming either option calls `switch_load_game_by_index_and_init()` the same as a normal load; Load additionally calls `load_game_state()` right after. Declining a load never deletes the old save file - like both existing platforms, nothing calls `delete_game_state()` today, so an unwanted save just sits until the next real exit silently overwrites it. This is the **Ask** mode of the Load State Behavior setting above; **Auto-Load** skips straight to the load without ever showing this screen, and **Never Load** skips straight to a fresh start instead - either way `g_load_prompt_active` never gets set, so this screen simply never renders. Debug mode forces the same fresh-start path regardless of what's set here (see above).
- Not implemented: any UI for a *manual* save/load independent of "leaving the game" (Android and 3DS don't have one either, both save purely as a side effect of returning to the menu).
- **Remembers the last game played across app restarts**: whenever `switch_unload_current_game()` actually saves (i.e. not under debug mode), it also sets `g_last_game_played_ref` to that game's `ref` and calls `switch_settings_save()`, writing it to `yokoi_settings.txt` as `lastgameplayed=<ref>`. `switch_get_default_game_index()` (`switch_game_loader.cpp`) checks this first on the next launch, ahead of the older per-manufacturer restoration mentioned below - so reopening the app lands you back on whatever you were actually playing, not wherever the list happened to be scrolled to.

Each entry shows the game's console-art PNG as a thumbnail (contain-fit into a fixed-size box - scaled up to touch the box's width or height, whichever binds, without stretching or exceeding it, then centered on both axes), framed in the accent color, with manufacturer/name/index text below.

**Text rendering**: went through two approaches before landing on the current one, worth knowing about if text ever looks wrong again:
1. First pass bundled `gfx/texte_3ds.png` (3DS's own bitmap font atlas) via ROMFS. This rendered every glyph as its own horizontal mirror image - the game-asset UV mirroring correction (`switch_screen.cpp`'s `kUvFlipX`, needed for CONVERT_ROM-pipeline PNGs) was wrongly applied to this separately-authored, non-mirrored asset.
2. Fixing the mirroring didn't fix it either - text was still garbled. Rather than keep debugging a hand-authored 128x128 grid atlas that only covers a fixed Latin subset anyway, switched to **FreeType against Switch's own shared system font** (`plGetSharedFontByType`), the same approach Hekate-Toolbox itself uses. Each glyph is rasterized once per exact pixel size and cached as its own small GL texture (`switch_ui.cpp`'s `g_glyph_cache`), tinted via the existing shader's alpha-only mode. No bundled font asset, no ROMFS, no atlas coordinate math to get wrong - and it covers whatever characters the shared font has, not just what the old table listed.

**Thumbnail cropping**: console-art PNGs aren't standalone images - like segment/background art, they're a sprite cropped out of a larger canvas via `GW_rom::console_info` (`[2]=u [3]=v [4]=w [5]=h`), same as the in-game console overlay in `switch_screen.cpp`. The first menu pass sampled the *whole* PNG, which is why the thumbnail showed as a big box with a small, oddly-positioned image inside - fixed by reading `console_info` and cropping the same way the in-game overlay does.

### What's deliberately not done yet

- "Top screen only" toggle (see the Settings section above)
- Cross-session persistence of "last game *per manufacturer*" - `switch_menu.cpp` keeps *that* in memory for the current run only, unlike Android's `yokoi_menu_selection.cpp` which also persists it via `save_last_selected_game()`. This is now largely moot for the launch-time case though: `switch_get_default_game_index()` prefers the simpler `lastgameplayed` value (see "Save states" below) whenever it resolves to a real game, and only falls back to this per-manufacturer mechanism (and then to Donkey Kong Jr./index 0) when it doesn't - e.g. before any game has ever been saved.
- No dedicated `switch` CONVERT_ROM target profile - by design. This build targets the existing `rgds` pack format directly (same `yokoi_pack_rgds.ykp` filename Android's `nativeInit()` hardcodes, and the same `YOKOI_ROMPACK_REQUIRED_CONTENT_VERSION=3` Android requires), so a pack already generated for Android works here unmodified. See "Testing on hardware" below.

## Why Android, not 3DS, is the template for the rest

- **Rendering**: the 3DS renderer ([`3ds_screen.h`](../source/virtual_i_o/3ds_screen.h)) is built on `citro3d`, which is 3DS-only silicon. The Android renderer ([`yokoi_gl.cpp`](../android/app/src/main/cpp/render/yokoi_gl.cpp)) is plain OpenGL ES 3.0 with generic shaders — the Switch portlibs provide EGL/GLESv3 via Mesa/nouveau, so that renderer is the right base, swapping `ANativeWindow` for libnx's `NWindow`. (One real difference: Switch homebrew has no linkable `libGLESv3` to call into directly like Android does - `gl*` calls have to go through `glad`'s runtime-loaded function pointers instead, via `eglGetProcAddress`.)
- **Single-screen layout**: [`yokoi_layout.cpp`](../android/app/src/main/cpp/core/yokoi_layout.cpp) already solves "how do you show a dual-screen Game & Watch on one physical display" (stacks the two G&W panels vertically or side-by-side into one canvas). Switch has the same one-screen constraint, so this is reused as-is.
- **Input polling**: ironically closer to 3DS here. `hidScanInput()`/`hidKeysHeld()` in [`3ds_input.cpp`](../source/virtual_i_o/3ds_input.cpp) maps almost 1:1 onto libnx's `padUpdate()`/`padGetButtons()` — more directly than Android's JNI touch/controller bridge does.
- **No Java/JNI layer needed**: Switch homebrew is plain C/C++ with no OS-level UI framework to bind to, so the Android `MainActivity`/JNI glue (`android/app/src/main/java/...`, `android/app/src/main/cpp/jni/...`) has no Switch equivalent — that's net deleted work, not added.

## Controls

**Menu**: D-pad Left/Right = prev/next game, D-pad Up/Down = prev/next manufacturer (or by sort group - see below), **A** = play, **Minus** = cycle sort mode, **Plus** = settings. The **left stick mirrors the D-Pad** here too.

**In-game**: mirrors the 3DS role mapping (`3ds_input.cpp`): D-pad = left/right G&W controls, A/B/X/Y = right-side controls, **L = Time**, **+ = Game A**, **− = Game B**. B is a real gameplay input here (some games use it), so it's *not* a back-to-menu shortcut. The **left stick mirrors the D-Pad** here too, and the **right stick mirrors A/B/X/Y** (X=up, A=right, B=down, Y=left - the physical diamond layout of the buttons it stands in for) - but gameplay-only, unlike the left stick's D-Pad mirroring, which also works on menus.

**Stick handling** (`switch_input.cpp`): both come for free from libnx's own `HidNpadButton_Stick{L,R}{Up,Down,Left,Right}` pseudo-buttons - synthesized from the stick position crossing libnx's internal deadzone, already part of the same bitmask `padGetButtons()`/`padGetButtonsDown()` return, no manual analog reading needed. The left stick's bits are folded directly into the real D-Pad bits before anything else touches them, so every existing D-Pad check (menu navigation, the in-game CTL_DPAD_* mask) picks it up automatically with no separate code path. The right stick's bits are folded into the in-game CTL_A/B/X/Y mask instead of into the raw button bits - that mask is only ever read by the gameplay branch of `main.cpp`'s loop (menu navigation reads the raw bits, never this mask), which is what keeps it out of menus without needing an explicit "are we in a menu" check.

Holding **ZL + ZR** opens the in-game settings screen (pausing the game) from gameplay - the only way to pause/menu out once a game is running. From there, **B** resumes in place, or **A** on "Return to Main Menu" drops back to the game list (saving state first, unless debug mode is set - see the Settings section above). From the game list itself, **L + R + Plus** quits to hbmenu instead.

## Building

Requires the `switch-dev` group from devkitPro (devkitA64 + libnx + the `switch-glad`, `switch-mesa`/EGL portlibs), plus `switch-freetype` (menu text) and its dependencies (`switch-harfbuzz`, `switch-libpng`, `switch-zlib`, `switch-bzip2`). On this machine these were added with:

```
pacman -S switch-glad switch-freetype switch-harfbuzz switch-libpng switch-zlib switch-bzip2
```

The Makefile links freetype/harfbuzz/libpng/zlib/bz2 directly by path rather than via `pkg-config --libs freetype2` (freetype's own recommended way to get its link flags) because `PKG_CONFIG_PATH` isn't set outside devkitPro's bundled MSYS2 shell - see the comment above `LIBS` in `switch/Makefile` if that ever needs revisiting.

**From devkitPro's own bundled MSYS2 shell** (`C:\devkitPro\msys2\msys2.exe`, which has `DEVKITPRO=/opt/devkitpro` pre-mounted correctly), building should just be:

```
cd switch
make
```

**From a plain Git Bash / non-devkitPro shell** (like the one this session used), two things need workarounds:
- `DEVKITPRO`'s auto-derived `DEVKITPATH` (used to build `PORTLIBS_PATH`) is computed via a `sed` pipeline in `devkitA64/base_tools` that doesn't survive make's `$(shell ...)` in this shell — pass `DEVKITPATH=` explicitly to skip it.
- GNU Make on this system does not forward `TMP`/`TEMP` from the parent shell into recipe subprocesses, and the native (mingw-hosted) compiler falls back to an unwritable `C:\WINDOWS\` for temp files without them — pass them as `Windows-style` (backslash) command-line make variables.

The verified working command from `switch/`:

```bash
export PATH="/c/devkitPro/devkitA64/bin:/c/devkitPro/tools/bin:$PATH"
make DEVKITPRO=/c/devkitPro DEVKITPATH=/c/devkitPro 'TMP=C:\Users\<you>\AppData\Local\Temp' 'TEMP=C:\Users\<you>\AppData\Local\Temp'
```

This produces `yokoi_switch.nro` (confirmed building clean against the full emulator core, ~7.5 MB - freetype/harfbuzz/libpng/zlib statically linked for menu text account for most of the growth from the pre-menu ~6 MB).
